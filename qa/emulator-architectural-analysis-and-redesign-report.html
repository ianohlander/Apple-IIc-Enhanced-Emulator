Can the emulator core in src/emulator/ be remade from scratch without breaking anything else?

YES, ABSOLUTELY. Because the application was architected around Object-Oriented principles (OOP), the Facade Pattern, and the Single Responsibility Principle (SOLID), the emulator engine is completely decoupled from the rest of the application.

All user interface panels, retro chassis skins, mechanical keyboard inputs, and flyout hardware studios (ImageWriter II, Slinky RAM, SmartPort HD, Mockingboard, 7-slot bus, Hex Viewer, Debugger) communicate exclusively through the single facade class Apple2cUltra in src/emulator/apple2c.ts. None of the UI components depend on internal 65C02 instruction decoders, memory banking latches, or Disk II stepper timings. The entire emulator core can be rebuilt from scratch or replaced as a drop-in modular unit without touching a single line of UI, layout, or styling code.

Root Cause Analysis of ACS Artifacts & World Games Failure

01. ACS "Rivers of Light" Text Artifacts

SCRAMBLED MMU & FONT TRUNCATION

When selecting "M" (Make Adventure) and choosing "Rivers of Light", the screen displayed:

Defect A — MMU Softswitch Bit Scrambling:
In index-standalone.html lines 5598–5605, the read-only status switches at $C011..$C01F were mapped to incorrect properties: $C011 read ramrd (should be Bank 2), $C012 read ramwrt (should be LC RAM read), and $C014 read altzp (should be RAMWRT). When ACS's 65C02 Forth disk copier queried RAM write-protection, it received bogus hardware states.
Defect B — Incomplete Character ROM Font Table:
The authentic disk code called the text routine with lowercase instructions: "Insert adventure disk (Rivers of Light) in drive 2, then press return.". In DEFAULT_CHARSET_ROM and the standalone generator, glyph bit definitions ended at ASCII 0x60. All lowercase letters (0x61..0x7A) mapped to blank zeros. Only uppercase headers, parentheses, and punctuation rendered, leaving massive blank gaps!

02. World Games Disk 1 Total Boot Failure

PROPRIETARY VORPAL FASTLOADER

Epyx's World Games disk 1A fails to boot and immediately crashes on cycle 1:

[BOOT] Track 0 Sector 0 Loaded to $0800
[CPU] JMP $0801 -> Opcode 0x00 (BRK) Executed!
[HALT] System crashed on Cycle 1. All Track 0 data was zeros.
Defect C — Parser Flaw (Missing Sector Headers):
World Games uses Epyx's proprietary Vorpal Fastloader. Vorpal does NOT use standard DOS 3.3 address markers ($D5 $AA $96). The WOZ parser exclusively checked for DOS 3.3 headers; finding none, it filled sector 0 with zeros. When the boot sequence jumped to $0801, the 65C02 executed $00 (BRK) and crashed instantly.
Defect D — High-Level Intercept "Cheating":
Instead of resolving the raw Disk II bitstream latch, the previous developer introduced Apple2cWorldGamesEngine and Apple2cAdventureConstructionSetEngine inside index-standalone.html. These classes drew mock vector graphics directly to the canvas, bypassing the CPU and disk completely!

03. 95% Incomplete System ROM (The "NOP Sled" Anti-Pattern)

MISSING AUTHENTIC FIRMWARE
What Exists in defaultRoms.ts:

• Total ROM size: 32,768 bytes.
• Initialized with: rom.fill(0xEA) (32 KB of NOP instructions).
• Hand-coded assembly: Only ~500 bytes of partial stubs (VTAB, partial HOME, fake Applesoft banner).
• 98.5% of the Apple //c firmware is completely missing!

What Authentic Software Requires:

• Commercial disks call dozens of un-stubbed Monitor entry points ($FD8E CROUT, $FD6A GETLN, $F94A PRBL2, $FDF0 COUT1, $FD1B KEYIN).
• Every un-stubbed call hits 0xEA, slides across thousands of NOPs, and crashes.
• Attempting to reverse-engineer thousands of 6502 subroutines one-by-one is the textbook definition of "whack-a-mole".

🛡️ Single Responsibility Principle (SRP)

Each component in src/emulator/ has exactly one reason to change:
• CPU65C02 only executes opcodes against a memory bus interface.
• Apple2cMMU only manages 128KB banking and softswitch latches.
• Apple2cVideo only translates VRAM bytes into pixel buffers.
• DiskIIController only streams disk nibbles and controls the drive motor/head.

🔌 Dependency Inversion Principle (DIP)

High-level UI components do NOT depend on low-level emulator details. The UI depends exclusively on high-level abstractions exposed by Apple2cUltra. Any new emulator implementation that satisfies this public contract will function seamlessly with 0% UI regression.

🖥️ The "Dummy Terminal" Pure Hardware Pipeline

Exactly 1 Ingress and 1 Egress — Zero HLI Overrides

The user's mandated "Dummy Terminal" architecture requires that the emulator behave strictly like an authentic hardware terminal connected to a vintage Apple //c chassis. There is exactly ONE ingress pipeline and exactly ONE egress pipeline:

1. SINGLE INGRESS PIPELINE User -> Hardware Latch
User Keystroke ➔ ASCII Conversion
➔ Write $C000 (Set Bit 7 Strobe)
➔ Read $C010 (Clear Strobe)
Strict Rule: NO JavaScript pre-parsing, NO synthetic BASIC command intercepts, NO spoofed menu handlers. Keystrokes enter hardware latches exclusively.
2. SINGLE EGRESS PIPELINE Physical VRAM -> CRT Display
Physical VRAM ➔ $0400-$07FF / $2000-$3FFF
➔ Apple2cVideo Rasterizer
➔ HTML5 2D Canvas Buffer
Strict Rule: NO mock screen redraws, NO synthetic vector lines, NO fake adventure logs. Every pixel rendered on the canvas originates strictly from 65C02 memory bytes.
