Executive Architecture Finding

The current emulator implementation suffers from a critical architectural defect: High-Level Language (HLL) Simulation Over-reach. Instead of executing real 6502/65C02 machine language code inside the CPU core using authentic ROM binaries, portions of the application (specifically index-standalone.html and high-level input handlers) have been simulating BASIC syntax parsing, variable storage, arithmetic evaluation, screen scrolling, and vector graphics in TypeScript/JavaScript.

This approach creates an endless maintenance burden where every magazine scan, DSK disk image, and machine-code routine requires bespoke JavaScript patches. The 65C02 CPU must be the sole source of truth. The emulator must solely emulate the CPU, memory bus, and hardware softswitches, while clean-room 65C02 system ROM images handle all BASIC interpretation, monitor input, line buffering, and floppy disk execution.

📊 Comprehensive Function & Domain Audit

Current State vs Pure 65C02 Standard
DOMAIN 1: BASIC Interpreter & Tokenizer Subsystem
CURRENTLY FAKED IN JAVASCRIPT
Current Implementation (Defective):

• executeBasicStatement() parses strings in JavaScript.
• evalBasicExpr() converts BASIC math into JS Function() calls.
• Variables stored in JS object this.basicVars = {}.
• Program lines stored as JS strings in an array.
• Result: Incompatible with machine code calls, zero-page pointers, and vintage magazine idioms.

Pure 65C02 Target Architecture:

• 12KB Applesoft BASIC ROM at $D000–$F7FF executes entirely on the 65C02 CPU.
• Program tokenized into 6502 binary bytes in RAM starting at $0801 (TXTTAB).
• Variables allocated in RAM at VARTAB ($69/$6A) and arrays at ARYTAB ($6B/$6C).
• Floating point operations run via 6502 FAC1 registers ($9D–$A2).

DOMAIN 2: System ROM & Monitor Firmware ($F800–$FFFF)
MINIMAL STUB IN DEFAULTROMS.TS
Current Implementation (Defective):

• defaultRoms.ts only contains ~40 bytes of hand-written NOPs and minimal loops.
• Monitor routines (GETLN $FD6A, RDKEY $FD0C, CROUT $FD8E, CLEOL $FC9C, CLEOS $FC42, PRBL2 $F94A) are missing or stubbed.
• Result: CPU cannot parse monitor commands or boot disks without high-level hacks.

Pure 65C02 Target Architecture:

• 2KB 65C02 System Monitor ROM at $F800–$FFFF.
• Full line editing into input buffer $0200–$02FF.
• Screen windowing math (WNDLFT $20, WNDWDTH $21, WNDTOP $22, WNDBTM $23, CH $24, CV $25).
• Built-in 65C02 Disassembler ($F88E) and Mini-Assembler ($F666).

DOMAIN 3: Storage & Disk II Controller Subsystem
HARDWARE PARTIALLY READY • ROM NEEDED
Current Implementation:

• diskII.ts implements 6-and-2 GCR track nibblizing and phase stepping.
• Softswitches $C0E0–$C0EF route phase coils and data register correctly.
• Defect: The 256-byte Slot 6 Disk II Boot ROM ($C600–$C6FF) is not mapped, preventing the 6502 CPU from executing the cold boot sequence itself via PR#6 or reset.

Pure 65C02 Target Architecture:

• 256-byte clean-room Disk II Firmware at $C600–$C6FF.
• 6502 machine code reads Sector 0 from Track 0 directly into RAM at $0800.
• Sector 0 code loads DOS 3.3 / ProDOS image into high memory.
• Zero TypeScript intervention in disk reads/writes.

DOMAIN 4: Keyboard Input & Softswitches ($C000–$C0FF)
NEEDS LATCH CLEANUP
Current Implementation:

• Keyboard events intercepted in JavaScript, converted to character strings, and passed to high-level statement handlers.
• Physical key strokes do not reliably set the hardware latch at $C000 with strobe bit 7 (| 0x80).

Pure 65C02 Target Architecture:

• DOM keydown event only does one thing: mmu.lastKeyPressed = ascii | 0x80.
• 65C02 CPU reads $C000 in its ROM KEYIN ($FD1B) loop.
• 65C02 clears strobe by reading/writing $C010.
• Zero UI interception or string accumulation.

DOMAIN 5: Video VRAM & Hi-Res Graphics Rendering
VRAM RASTERIZER READY • CODE MUST RUN ON CPU
Current Implementation:

• Standalone version used custom JS functions (handleHplot, drawShape) calculating pixel coordinates in JavaScript.
• Defect: When vintage programs call HPLOT or XDRAW, the CPU is not executing the Applesoft ROM graphics algorithms; JavaScript is doing the math.

Pure 65C02 Target Architecture:

• 65C02 executes Applesoft ROM routines: HPLOT0 ($F457), HLIN ($F53A), XDRAW ($F65D), DRAW ($F601).
• CPU writes directly into Hi-Res VRAM ($2000–$3FFF Page 1, $4000–$5FFF Page 2).
• The canvas display only rasterizes the raw VRAM bytes to screen (like a real CRT monitor).

Technical Roadmap: Pure 65C02 & Clean-Room ROM Implementation

Phase 1: Clean-Room 32KB System ROM Assembly ($C000–$FFFF)

Construct a complete, era-accurate 32KB binary ROM image containing:

  • $C600–$C6FF (256 bytes): Disk II 16-Sector Boot Firmware (GCR decode & Track 0 boot).
  • $D000–$F7FF (10,240 bytes): Applesoft BASIC 6502 Interpreter (full token table, evaluator, math pack, HGR/LORES graphics engine).
  • $F800–$FFFF (2,048 bytes): 6502 Ultra System Monitor & Autostart ROM (Reset vectors, KEYIN, GETLN, COUT, memory inspection).

Phase 2: Remove All High-Level BASIC Parsing in TypeScript

Completely delete executeBasicStatement, evalBasicExpr, this.basicVars, and JavaScript loop controllers. When the user pastes or enters BASIC code, feed the characters sequentially into the 65C02 keyboard latch at $C000. The 65C02 CPU will read the characters, parse them with its ROM tokenizer, and store them directly into program memory at $0801.

Phase 3: Verify 65C02 CPU as Single Source of Truth

Verify with automated test suites that 100% of CPU instructions, zero-page pointers, floppy stepper motor phases, and video memory pixels are generated by the 65C02 CPU core stepping cycle-by-cycle through memory.
